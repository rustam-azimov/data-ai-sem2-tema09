От API до документной базы

Получите JSON каталога товаров, исследуйте вложенные поля, выполните пять запросов MongoDB и представьте те же данные двумя связанными таблицами. Объясните, какая модель удобнее для ваших задач и что меняется при раскрытии массива отзывов.

Результат работы: один ZIP с отчётом PDF, исходными JSON, таблицами CSV и файлом queries.js. Работа индивидуальная; вариант определяется по шестизначному номеру ИСУ. Можно пройти весь маршрут в браузере или получить данные скриптом Python. Установка MongoDB и аккаунт MongoDB Atlas не нужны.

Выберите свой вариант

Введите ровно шесть цифр ИСУ. Правило: 1 + Number(isu) % 3. Ведущие нули сохраняйте в отчёте. Например, для 123456 получается вариант 1. Каждый вариант — десять исходных товаров из сохранённого ответа DummyJSON на 30 товаров.

Введите ИСУ или вычислите вариант вручную по формуле.

Варианты и адреса API

Два разных набора данных

products_training.json содержит 12 специально изменённых учебных товаров: изменены число и оценки отзывов, добавлен reviews.verified, изменено наличие brand. Эти данные используются в примерах и встроенных таблицах тренажёра. Домашняя работа выполняется на raw-данных своего варианта: variant_1.json, variant_2.json или variant_3.json. В raw-отзывах поля verified нет. Не добавляйте его и не переносите числа из учебных примеров.

Live API может измениться. Эталонные числа курса относятся к сохранённому снимку, а ваши результаты — к приложенному вами JSON. Не смешивайте снимок и live в разных шагах. При отличиях live от снимка укажите это в отчёте; при изменении ID используйте статический вариант и честно обозначьте источник.

Шаг 1. Получите данные и зафиксируйте источник

Адрес строится так: https://dummyjson.com/products?limit=10&skip=(variant-1)*10. Выражение в скобках нужно вычислить: браузер не вычисляет его внутри URL. Для вариантов используйте готовые ссылки выше.

Маршрут без кода

  1. Откройте URL своего варианта. Сохраните полный ответ API как api_response.json. Скопируйте только массив из поля products в отдельный products.json: файл должен начинаться с [, заканчиваться ] и содержать десять объектов.
  2. Проверьте число товаров и уникальность id. Для варианта 1 ожидаются ID 1–10, для 2 — 11–20, для 3 — 21–30. Сохраните полный URL и дату с часовым поясом; если доступен HTTP-статус в сетевой панели браузера, запишите его. Не придумывайте статус, если его не проверяли.
  3. Если API недоступен или набор изменился, скачайте статический файл своего варианта. Используйте его как products.json. В отчёте напишите «статический снимок курса», путь к файлу и дату скачивания. Дата скачивания не является датой исходного API-запроса. Если исходная дата неизвестна, так и укажите. Полный снимок доступен как api_response.json.

Маршрут Python

Скачайте download_api.py. Скрипт использует стандартную библиотеку Python 3 и urllib; устанавливать requests и другие пакеты не нужно. Выполняйте из корня репозитория, заменив номер варианта:

python3 scripts/download_api.py --variant 2 --output lab09_live

# Явный переход к сохранённому ответу на 30 товаров:
python3 scripts/download_api.py --variant 2 --output lab09_snapshot \
  --snapshot 05_ДАННЫЕ_СТУДЕНТАМ/api_response.json

Папка результата должна быть новой или пустой. В ней появятся api_response.json (исходные байты ответа или снимка), products.json (выбранные десять товаров) и metadata.json. При ошибке сети скрипт завершится с сообщением; автоматической подмены live снимком нет. Тайм-аут сетевой операции — 20 секунд.

Скрипт проверяет HTTP 200 для live, оболочку products, целочисленные total / skip / limit, пагинацию, число и уникальность ID, ожидаемый порядок ID. Это проверка получения, а не полный профиль каждого поля. В snapshot-режиме входом служит полный ответ на 30 товаров, а не файл variant_2.json. Метаданные отдельно хранят режим, URL варианта, URL источника, время обработки, фактическое время live-загрузки, ID и SHA-256 исходных байтов. Для снимка HTTP-статус и исходная дата загрузки остаются неизвестными; время обработки их не заменяет.

В отчёт: ИСУ, вариант, способ получения, URL, дата и часовой пояс, источник live/snapshot, число документов и список ID. Если получали вручную, приложите краткую карточку источника metadata.json с этими сведениями; неизвестные значения обозначьте null.

Шаг 2. Составьте профиль JSON

Откройте выбранный products.json в браузере, редакторе или тренажёре JSON. Для домашней работы загружайте свой файл; встроенные учебные документы служат только для подготовки. Оболочка ответа API — объект с метаданными, отдельный файл товаров — массив документов.

  1. Опишите единицу наблюдения: один документ соответствует товару, id — его идентификатор. Проверьте десять документов и десять уникальных ID.
  2. Составьте таблицу полей: путь, JSON-тип, смысл, число документов с полем, число null и пример значения. Обязательно рассмотрите id, title, category, price, brand, dimensions.width, tags, reviews и reviews[].rating / reviewerName. Типы и пропуски определяйте по всем десяти документам. Для полей отзывов отдельно укажите число самих отзывов, где поле присутствует.
  3. Объясните различие отсутствующего ключа, null, пустой строки и пустого массива. Не заменяйте пропуски нулём. Запишите число отзывов каждого товара и их общее число; проверьте числовой тип price, width и оценок.
  4. Приведите один сокращённый пример своего документа с dimensions и reviews. Покажите путь к ширине, имени автора первого отзыва и элементу tags; отсутствие первого отзыва тоже допустимо. Даты в исходном JSON являются строками, пока вы явно не преобразовали тип.

Укажите выявленные ограничения данных: DummyJSON — искусственный каталог, отзывы не подтверждают реальных покупок, поля могут отсутствовать. Содержимое имени автора само по себе не доказывает достоверность отзыва.

Шаг 3. Выполните пять настоящих MongoDB-запросов

Откройте Mongo Playground. Это среда выполнения MongoDB-запросов в браузере; регистрация в MongoDB и подключение к Atlas не требуются. Наш тренажёр помогает разобраться с документами, а эти пять запросов нужно выполнить именно в Mongo Playground.

  1. В поле Database замените демонстрационные документы полным массивом из своего products.json. Не вставляйте туда всю оболочку API, метаданные или JSONL.
  2. В поле Query введите db.collection.find(), запустите запрос и проверьте, что вернулись ваши десять товаров. В примерах коллекция называется collection; если вы изменили имя в конфигурации, согласуйте его с запросом.
  3. Выполняйте по одному запросу из списка ниже. Все пять сохраните в queries.js с комментариями «Запрос 1» … «Запрос 5». Не вставляйте все пять команд одновременно в поле Query.
  4. Для каждого запроса добавьте в PDF код, скриншот фактического результата (для длинного результата достаточно видимого фрагмента), число возвращённых строк или документов и объяснение смысла результата. Для полной воспроизводимости сохраните текстовые результаты в query_1.json … query_5.json. Пустой результат допустим, если он подтверждён исходными данными.

Запрос 1. Товары с ценой не ниже 20

db.collection.find(
  { price: { $gte: 20 } },
  { _id: 0, title: 1, price: 1 }
)

В результате должны остаться только title и price. Проверьте границу: цена ровно 20 проходит условие. Не подставляйте число строк из учебной выборки.

Запрос 2. Ширина больше 10

db.collection.find(
  { "dimensions.width": { $gt: 10 } },
  { _id: 0, id: 1, title: 1, "dimensions.width": 1 }
)

Точка задаёт путь во вложенном объекте. Ширина ровно 10 не проходит. Не приписывайте числам единицы измерения, если источник их явно не сообщает.

Запрос 3. Хотя бы один отзыв с rating ≥ 4 и существующим reviewerName

db.collection.find(
  { reviews: { $elemMatch: {
    rating: { $gte: 4 },
    reviewerName: { $exists: true }
  } } },
  { _id: 0, id: 1, title: 1, reviews: 1 }
)

$elemMatch требует выполнения обоих условий одним и тем же элементом массива. Два независимых условия по точечным путям могут совпасть с разными отзывами. $exists: true проверяет наличие ключа, включая значение null; это не проверка непустого имени. Проекция выводит весь массив reviews, а не только подходящий отзыв. Укажите хотя бы один конкретный подходящий отзыв. Условие verified здесь не используется: этого поля в raw нет.

Контрпример: зачем нужен $elemMatch?

В исходных вариантах reviewerName есть у всех отзывов, поэтому два способа записи могут вернуть одинаковый результат. Отдельно от исходного каталога проверьте этот искусственный документ в Playground:

[{ "id": 9001, "reviews": [
  { "rating": 5 },
  { "rating": 2, "reviewerName": "Учебный автор" }
] }]

Сравните ваш запрос 3 с db.collection.find({"reviews.rating": {$gte: 4}, "reviews.reviewerName": {$exists: true}}). Предскажите число найденных документов и объясните различие: подходящий рейтинг и существующее имя принадлежат разным отзывам. Не добавляйте этот пример к десяти raw-товарам.

Запрос 4. Число товаров и средняя цена по категории

db.collection.aggregate([
  { $group: {
    _id: "$category",
    avg_price: { $avg: "$price" },
    count: { $sum: 1 }
  } }
])

Порядок строк без сортировки не гарантируется; сравнивайте категории по _id. Одна строка результата соответствует категории, а поле _id хранит её название. Сумма count должна быть 10. Среднее относится к исходным товарам; округляйте только итоговое отображение до двух знаков, сохраняя исходную точность для расчётов.

Запрос 5. Раскройте отзывы и подсчитайте их по id товара

db.collection.aggregate([
  { $unwind: "$reviews" },
  { $group: { _id: "$id", count: { $sum: 1 } } }
])

После $unwind одна строка соответствует одному отзыву. Сумма count равна общему числу отзывов из шага 2. Товары с пустым, отсутствующим или null-массивом в таком запросе исчезают; для сверки дополните их нулями по списку исходных ID. Не применяйте preserveNullAndEmptyArrays: true вместе с безусловным $sum: 1 для подсчёта отзывов: строка товара без отзыва ошибочно даст единицу.

Справка: семантика $elemMatch, раскрытие массива $unwind, пагинация DummyJSON.

Шаг 4. Преобразуйте документы в две таблицы

Используйте тот же products.json, на котором выполнялись запросы. Без кода загрузите его в тренажёр 09·1 «Разбери ответ API», шаг 4: «Загрузить JSON своего варианта». Скачайте products.csv и reviews.csv. Встроенные таблицы тренажёра относятся только к training и для сдачи не подходят. Экспорт сохраняет аналитические поля для текущих задач; полный исходный документ остаётся в products.json. Таблицы также можно получить своим кодом Python.

Минимальная схема CSV
ФайлОдна строкаОбязательные столбцы
products.csvТовар; 10 строк без заголовкаid, title, category, price, dimensions_width
reviews.csvОдин исходный отзывproduct_id, review_index, rating, reviewerName, comment, date

products.id — первичный ключ, reviews.product_id — внешний ключ на него. review_index — позиция отзыва в исходном массиве, начиная с 0; пара (product_id, review_index) уникальна. Два одинаковых по тексту отзыва не удаляйте: это две исходные позиции. Число строк reviews.csv равно сумме длин массивов. Товар без отзывов остаётся в products.csv и не создаёт фиктивного отзыва.

Экспортируйте CSV в UTF-8 с заголовками и запятой-разделителем, числа — с точкой. Значения с запятыми, кавычками и переносами строк заключайте в кавычки по правилам CSV. Пропуски можно оставить пустыми ячейками, но запишите это соглашение в отчёте: CSV сам по себе не различает отсутствующий ключ, null и пустую строку. Исходный JSON сохраняет эти различия.

  1. Проверьте уникальность ключей, отсутствие отзывов с неизвестным product_id и совпадение числа отзывов по каждому id с запросом 5. Это связь products.id = reviews.product_id; соединение по названию или имени автора некорректно.
  2. По исходной products.csv посчитайте для каждой category count товаров и avg_price. Сопоставьте с запросом 4 в таблице: category, Mongo count, CSV count, Mongo avg_price, CSV avg_price, разница. Числа товаров должны совпасть точно; средние сравнивайте до округления с допуском 0,000001.
  3. Соедините products и reviews по ключу. Для наглядности можно использовать SQL ниже или аналогичные действия конструктора/табличного редактора. Для left join число строк не меньше 10; для inner join равно числу отзывов. Подсчёт строк после join обычно не равен числу товаров.
  4. Снова посчитайте count и avg(price) по category уже после inner join и сравните с исходными товарами. Сохраните обе версии в category_comparison.csv, отдельно обозначив исходный count товаров и count строк соединения. Объясните совпадение или различие на фактическом числе отзывов. Если у всех товаров категории одинаковое ненулевое число отзывов, среднее может совпасть; это не отменяет размножения строк.
-- Иллюстрация соединения после импорта ваших CSV в SQL-инструмент:
SELECT p.id, p.title, p.category, p.price,
       r.review_index, r.rating, r.reviewerName
FROM products AS p
LEFT JOIN reviews AS r ON p.id = r.product_id;

-- База для сверки с Mongo-запросом 4:
SELECT category, COUNT(*) AS count, AVG(price) AS avg_price
FROM products
GROUP BY category;

-- Отдельный эксперимент: цена товара повторяется для каждого отзыва.
SELECT p.category, COUNT(*) AS joined_rows, AVG(p.price) AS avg_price
FROM products AS p
JOIN reviews AS r ON p.id = r.product_id
GROUP BY p.category;

Не исправляйте повторение цены через AVG(DISTINCT price): разные товары могут иметь одинаковую цену. Для среднего по товарам считайте по products либо предварительно возвращайте ровно одну строку на каждый id. Для числа товаров после соединения подходит COUNT(DISTINCT p.id), но inner join всё равно теряет товары без отзывов. В отчёте приведите пример своего товара, сколько строк он дал после раскрытия и почему.

Шаг 5. Проверьте помощь ИИ и выберите модель

Сначала сформулируйте свой вывод по результатам. Затем попросите доступного ИИ проверить один запрос или предложить схему хранения. Передавайте только нужный фрагмент искусственных учебных данных; номер ИСУ в запрос ИИ включать не требуется.

объект dimensions и массив reviews с rating и reviewerName.

Не добавляй поля, которых нет в описании. Затем проверь мой запрос: …

Приложите название модели/сервиса, дату, точный промпт, существенный фрагмент ответа и свою проверку на данных в Mongo Playground. Укажите, что приняли, что исправили и почему. Если ответ оказался верным, опишите конкретную проверку, которая это подтвердила. Ответ ИИ не заменяет результат выполнения. Если ИИ не использовали или сервис недоступен, честно укажите это и самостоятельно разберите возможную ошибку (например, выдуманное verified или AVG после join); оценка относится к качеству проверки и прозрачности, доступ к платному сервису не нужен.

Напишите обоснование выбора модели для каталога: какие операции удобнее с вложенными документами, а какие — с отдельной таблицей отзывов; как обновлять товар и отдельный отзыв; какие проверки ключей и типов нужны. Свяжите вывод с двумя своими результатами, включая сравнение среднего по category. Выберите документную, реляционную или смешанную модель для конкретного сценария и объясните компромисс. Формулировки «NoSQL всегда быстрее» и «JSON не имеет схемы» без условий и проверок не являются обоснованием.

Необязательно: неоднородные характеристики товаров

Предложите структуру characteristics для двух категорий с разными атрибутами: например, объём аромата и материал мебели. Это отдельное проектное расширение; таких новых значений нет в исходном raw, не добавляйте их в сдаваемый products.json и не выдавайте за ответ API. Покажите два явно синтетических документа, обсудите типы, обязательность полей и альтернативу «таблица характеристик». Дополнительный раздел не повышает максимум выше 10 баллов.

  4. queries.js с пятью MongoDB-запросами и query_1.json … query_5.json с полными фактическими результатами. Если есть собственный код преобразования, приложите его; для маршрута без кода достаточно описания действий.

PDF должен читаться без перехода по внешним ссылкам. Скриншоты показывают фактическое выполнение, а файлы JSON/CSV/JS позволяют повторить расчёты. Ссылку на Playground можно добавить, но она не заменяет эти файлы.

Проверка перед отправкой

  • Везде используются одни и те же десять raw-товаров своего варианта; источник и дата не подменены.
