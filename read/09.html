Данные с гибкой структурой и NoSQL

Как получить вложенные данные, задать им вопросы и выбрать способ хранения. Сквозной пример — каталог товаров, который используется в практике и домашней.

1. Карточка товара и таблица отчёта

В теме 8 мы связывали отдельные таблицы ключами. Теперь представим каталог: у аромата есть объём, у мебели — материал и размеры, у товара — несколько отзывов. В одной плоской таблице придётся выбирать: повторять товар для каждого отзыва, создавать столбцы review_1, review_2 или отделить отзывы в связанную таблицу.

Реляционная модель справляется с такими данными: например, через products, reviews и таблицу характеристик. Цена этого решения — дополнительные связи и преобразования при сборке карточки. Документная модель предлагает хранить часть связанных сведений внутри одного документа.

2. Как устроен JSON

JSON — текстовый формат обмена. Значение бывает объектом, массивом, строкой, числом, true, false или null. Объект содержит пары «ключ — значение», массив — упорядоченные элементы. Ключи и строки записываются в двойных кавычках; комментариев, undefined и завершающей запятой в стандартном JSON нет.

{
  "id": 2,
  "title": "Eyeshadow Palette with Mirror",
  "price": 19.99,
  "brand": null,
  "dimensions": {"width": 9.26, "height": 22.47, "depth": 27.67},
  "reviews": [{"rating": 5, "verified": true}]
}

Это сокращённый документ из изменённой учебной выборки. dimensions.width означает путь к ширине; reviews[0].rating — рейтинг первого отзыва в записи пути нашего JSON-тренажёра. Такой путь — способ обращения к структуре, а не часть синтаксиса самого JSON.

Число 19.99 и строка "19.99" имеют разные типы. Дата в обычном JSON передаётся строкой; календарную корректность и часовой пояс нужно проверять отдельно. Порядок полей объекта не должен определять смысл документа, а порядок элементов массива может быть существенным.

3. Отсутствие поля, null и пустой массив
Отсутствующее brand означает, что ключ не передан. "brand": null означает, что ключ есть и его значение явно пустое. Это может быть неизвестность или неприменимость — точное значение определяется договорённостью источника. Пустая строка — строковое значение, а "reviews": [] — существующий массив без элементов. Число 0 и false тоже не являются пропусками.
В учебной выборке 12 товаров: у четырёх brand отсутствует, у четырёх равен null, у четырёх содержит строку. Это специально подготовленные случаи, а не описание всего DummyJSON.
// Запросы MongoDB; это JavaScript-подобная запись, не JSON-файл
{ brand: null }                 // null ИЛИ отсутствующее поле: 8 товаров
{ brand: { $exists: false } }   // только отсутствующее поле: 4 товара
{ brand: { $exists: true } }    // ключ существует, включая null: 8 товаров
Что найдёт {brand: {$exists:true}}?
При экспорте в CSV такие состояния часто превращаются в одинаковую пустую ячейку. В нашем экспорте brand_state сохраняет различие missing/null/value, а исходный JSON остаётся обязательной частью работы.
4. Получение данных через API
API описывает, как запросить данные у сервиса. В учебном примере клиент отправляет HTTP GET на адрес ресурса products; параметры limit и skip управляют размером страницы и числом пропускаемых товаров.
GET https://dummyjson.com/products?limit=10&skip=0

{ "products": [ ... ], "total": 194, "skip": 0, "limit": 10 }
194 — total в сохранённом снимке от 8 ноября 2026 года. Живой каталог может измениться. products.length — число объектов именно в текущем ответе. Успешный HTTP-статус не доказывает полноту или правильность данных: нужно проверить структуру ответа, типы, идентификаторы и метаданные страниц.
  1. Сохранить исходный ответ, точный URL и дату получения с часовым поясом.
  2. Прочитать total, limit, skip и фактическое число объектов.
  3. Если нужен весь каталог, запрашивать следующие страницы и проверять отсутствие повторов id. Одной первой страницы недостаточно.
  4. Сопоставить уникальные id с ожидаемым объёмом. Если каталог меняется во время загрузки, offset-пагинация может давать пропуски или повторы; для воспроизводимого отчёта нужен согласованный снимок.
В тренажёре отдельно обозначены страницы локального каталога из первых 30 товаров и запрос к живому API. В домашней требуется только назначенный блок из 10 товаров, а не все 194. При недоступности сети разрешён явно подписанный снимок.

5. Документные базы и другие NoSQL-модели
База хранит данные и обслуживает запросы. В документной СУБД единицей хранения служит документ: именованные поля могут содержать вложенные документы и массивы. Документы объединяются в коллекции. В MongoDB внутренняя форма — BSON: бинарное представление с дополнительными типами, например ObjectId и датой. Поэтому JSON-файл, ответ API и документ MongoDB — связанные, но разные понятия.
Гибкая структура допускает разные наборы полей. Она не отменяет правил: id должен быть устойчивым, цена — числом, массив отзывов — массивом, обязательные поля — присутствовать. В MongoDB можно задавать валидацию схемы. Уникальность и доступные индексы также проектируются.

ШирококолоночнаяРазделы и строки, ориентированные на ключи доступаБольшие потоки событий с заранее выбранными запросами
NoSQL — общее название семейства подходов, а не единый язык и не обещание большей скорости. SQL-СУБД тоже могут хранить и запрашивать JSON, например PostgreSQL через jsonb. Выбор не сводится к противопоставлению «таблица или JSON».
6. Вопросы к вложенным документам
В MongoDB find отбирает документы. Условия по разным полям одного фильтра соединяются логическим И. Проекция определяет возвращаемые поля; фильтрация не превращает массив автоматически в отдельные строки.
db.collection.find({
  category: "fragrances",
  price: { $gte: 70 }
})
В учебной выборке подходят id 7, 8 и 10: три товара. Для ширины используется путь "dimensions.width". Независимые условия "reviews.rating": {$gte:4} и "reviews.verified":true могут совпасть в разных отзывах.
db.collection.find({
  reviews: { $elemMatch: {
    rating: { $gte: 4 },
    verified: true
  } }
})
$elemMatch требует, чтобы оба условия выполнил один элемент. В учебных документах verified:true добавлен первому отзыву, а рейтинг 5 — последнему. Для массивов длиной больше одного это разные отзывы. Независимые условия находят 9 товаров, $elemMatch — только 3, id 2, 6 и 10.
В отзывах [{rating:5,verified:false}, {rating:2,verified:true}] есть один подтверждённый отзыв с рейтингом ≥4?
В исходных вариантах домашней verified нет. Там используется reviewerName с $exists:true; отдельный искусственный контрпример помогает проверить понимание $elemMatch. Нельзя добавлять выдуманное поле в raw-данные, чтобы запрос начал работать.
7. Преобразование документов в таблицы
Перед преобразованием назовите единицу наблюдения. В products одна строка — товар; в reviews — отзыв. product_id связывает отзыв с товаром. Пара (product_id, review_index) различает позиции в исходном массиве, но при перестановке массива индексы меняются: это не постоянный идентификатор отзыва.
$unwind создаёт строку для каждого элемента массива. В стандартном режиме товары с пустым, отсутствующим или null-массивом исчезают. Опция preserveNullAndEmptyArrays может сохранить родителя, но полученную пустую строку нельзя считать настоящим отзывом.
До и после раскрытия reviews
В учебной выборке 12 товаров и 18 отзывов; три товара не имеют отзывов. После раскрытия остаётся 9 уникальных товаров. Цена повторяется для каждого отзыва, и среднее меняется с 407,24 до 669,38. Это изменение состава и весов наблюдений, а не изменение цен.
// Сводка по товарам: отзывы не раскрываются
 db.collection.aggregate([
   { $group: {
       _id: "$category",
       count: { $sum: 1 },
       avg_price: { $avg: "$price" }
   } }
 ])
Для среднего по товарам используйте products, а не строки соединения. AVG(DISTINCT price) не исправляет ошибку: разные товары могут иметь одинаковую цену. Для числа товаров после раскрытия можно считать уникальные id, но это не вернёт уже потерянные товары без отзывов.
В raw-вариантах домашней у каждого товара по три отзыва. Среднее после соединения поэтому может совпасть с исходным — это результат одинаковых весов, а не общее свойство преобразования.

8. Выбор хранения и проверка ИИ
Вложите данные, если их обычно читают вместе, размер вложения ограничен, а обновления удобно выполнять в рамках родителя. Для карточки можно вложить пять последних отзывов. Всю растущую историю удобнее рассматривать отдельно: коллекция reviews со ссылкой product_id позволяет независимо искать и модерировать отзывы.
Ссылки требуют дисциплины: нужно проверять существование родителя, согласованность идентификаторов и порядок обновлений. Дублирование имени или категории в документах ускоряет некоторые чтения, но усложняет изменения. Индекс может ускорить конкретный фильтр, при этом занимает место и увеличивает стоимость записи. Транзакции и соединения возможны и в документных СУБД; выбор определяется доступными механизмами и требованиями.
ИИ можно поручить предложить структуру, написать преобразование или объяснить запрос. В промпте задайте поля и типы, единицу наблюдения, обязательность сохранения всех id, правила обработки пустых массивов и формат результата.

Проверка результата: уникальность id, отсутствие отзывов без родителя, сумма длин массивов, сопоставление исходного и итогового агрегата. Синтаксически правильный JSON ещё не подтверждает верность структуры или вывода ИИ. Укажите модель, промпт, принятые изменения и свою проверку.
